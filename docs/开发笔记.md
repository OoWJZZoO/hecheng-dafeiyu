# 开发笔记（历史记录）

> 这是游戏开发过程中的工作笔记（原 README），按时间堆出来的设计决定、踩过的坑和量出来的数，留作参考。
> 里面的「用户」是指项目发起人，「作者」是动画原作者；个别路径、命令、分支（如微信版 `wxgame`）是当时的开发环境，本仓库不含，读到请当历史看。上手请先看根目录 [README.md](../README.md)。

《按下发送之后》的像素同人小游戏，玩法是「掉落合成」：从上方丢东西，两个同级的碰到就合成下一级，堆过红线结束。给粉丝免费玩。

- 纯网页：`index.html` + `game.js` + `pixui.js` + `vendor/matter.min.js`（Matter.js 0.20，MIT）。无构建步骤。改了 js 记得把 `index.html` 里的 `?v=N` 加一，不然浏览器读缓存。
- 界面全是像素风：`pixui.js` 用离线字模图（见下文和 `docs/像素字经验.md`）拼字、二值化、加描边投影，再最近邻放大；按钮/面板是 CSS box-shadow 做的缺角像素框；i/♪ 是字符画图标。所有界面在 360×704（2026-11-13 前是 360×640）的 `#ui` 层里排，和画布同倍缩放。
- 竖屏 360×704 逻辑分辨率（见下「屏幕适配」），关插值；按先顶到的一边撑满（不取整数倍）；触屏/鼠标拖动松手放下（2026-11-14 起没有键盘操作，只剩 `?showcase` 的调试快捷键）；最高分存 localStorage。
- 音效是 WebAudio 现场合成的 8-bit 方波，没用素材文件。

## 动画设计哲学（2026-11-11 用户定）

教程/相框动画是**实时渲染**的，循环天然可以每次略有不同。所以**不要为了把一个道理讲全，把一段动画越拖越长**；把情况拆成几段短的变体，让循环去轮播/随机，玩家看更多的「微不同循环」就能拿到更多信息，不必看完一轮。

- 摇一摇第二排：每一轮只推进一颗豆（0 颗淡色 → 2500 第 1 颗 → 10000 第 2 颗 → 20000 …），一轮 1.5–2.2 秒；玩家看一两轮就懂「进度条满 → 一颗金豆」，继续看会看到后面更高的门槛，不用在一轮里等 9 颗都飞完。大肥鱼相消：普通 / 一金一普通 / 双金三幕轮播；一金一普通的产豆数每轮随机 1 或 2，循环几次就能看到两种结果，不用在同一幕里把两种都演一遍。第三排的鱼豆会飞过卡片落进第二排九宫格；九宫格满了鱼豆照飞、到格子消失（不削减产出），第二排到下一个门槛才清零重开——两排各自短循环，玩家看几眼就能把「豆从哪来、满了会怎样」拼起来。
- 判断标准：新加一种情况时，先想「做成循环里的一个小变体 / 另一轮」还是「把原镜头拉长」；优先前者，单个镜头保持短。

## 性能和帧节奏（2026-11-14）

起因：群友用小米 15 的自带浏览器玩，**一进游戏就觉得卡**（不是堆满了才卡）；另外美梦模式堆多了会掉帧。手头没有那台手机，下面是在电脑上能复现、能量出来的部分。**真机上到底是哪一种，要请说卡的人在网址后面加 `?fps`（网址里已经有问号就加 `&fps`）截个图**，见下面「帧率小窗」。

### 查出来的跨平台问题（都已修）

1. **节奏对不上——最可能就是「一进去就卡」。** 逻辑是固定 60 步/秒；原来每帧「攒够 16.7 毫秒就走一步」然后直接画。屏幕正好 60Hz 时每帧一步，没事；不是 60Hz（90 / 120 / 144Hz 的手机，会自己变刷新率的屏）时，一帧里走 0 步、1 步还是 2 步来回变，球一顿一顿地动——帧率是满的，看着却卡，而且和球多球少没关系。小米 15 是 120Hz 的可变刷新率屏；用户自己的显示器是 180Hz，原来每个位置要停 3 帧。
   用 `tools/perf_web.cjs --scene fall` 量一个下落的球每帧挪了多少（画布像素）：

   | 刷新率 | 原来 | 现在 |
   |---|---|---|
   | 60Hz | 21.9 22.3 22.7 23.1 … | 21.9 22.3 22.7 23.1 …（一样） |
   | 90Hz | 18.5 **0** 18.9 19.3 **0** 19.8 20.2 **0** … | 12.0 12.3 12.4 12.6 12.9 … |
   | 120Hz | **0** 16.7 **0** 17.1 **0** 17.6 … | 每帧都动，位移和帧间隔成正比 |
   | 180Hz | **0** 14.9 **0 0** 15.3 **0 0** 15.8 … | 4.9 5.0 5.0 5.1 5.1 5.2 … |

   修法（`loop` / `render`）：逻辑还是 60 步/秒，**画的时候把每个球画在「上一步 → 这一步」之间按时间插值的位置上**（`lerpK`；每步之前把位置记在 `b.px / b.py / b.pa`，摇一摇的容器偏移同理）。物理没在走的时候（暂停、时停、教程）不插值。帧间隔先捋平再用（`frameGap`：估一个刷新周期，这一帧和它的整数倍差不多就按整数倍算）——有的浏览器时间戳只精确到毫秒，直接拿去插值球会微微发抖；捋平之后 60Hz 的屏和原来逐帧一模一样。
2. **跟着帧率走的动效。** 合成出来「弹一下」（`b.pop`）、震屏衰减、镀金冒金星、水里的气泡、成就横条和绶带上的金星，原来都写在绘制里「每画一帧推进一次」：120Hz 的屏上快一倍、密一倍（金星多一倍也是白花的性能）。现在都按步推进（`stepVisual` / `ambient` / `stepSeq`），所有设备一样。教程、图鉴、成就页的动画本来就是按步的。**用户自己的 180Hz 屏上会有变化**：金星比原来稀到三分之一、弹一下和震屏比原来长——这才是手机上一直看到的样子。
3. **追帧雪崩。** 机器慢、一帧里要补几步时，原来最多补 6 步：物理本来就算不过来的时候越补越慢（一帧 6 步物理 → 这一帧更长 → 下一帧还要 6 步），帧数直接掉到个位数。现在最多补 3 步，补着补着已经花掉 30 毫秒也不再补，剩下的时间丢掉——实在算不过来时游戏略微放慢，不再变成幻灯片（`MAX_STEPS` / `STEP_BUDGET`）。
4. **每帧白做的整屏操作**（显卡加速的画布上不显眼；画布没有硬件加速的浏览器、慢手机上是大头，而且和球数无关）：
   - 原来先画在中间画面 `scr` 上再整幅拷到 `cv`，手机上是 1080×2112 一比一的拷贝。现在画布一格不到 2 个物理像素时（`kc = 1`，手机上都是）**直接画在 `cv` 上**；大屏（`kc > 1`）才走原来的路。
   - 原来每帧把背景放大贴满画布。背景本来就在后面那张全屏的 `#backdrop` 上，现在**游戏画布是透明底**、叠在它上面，不再画背景（同一张图、同样的对齐）。
   - 「清空画布」和「铺容器的半透明奶油底」并成一步（`copy` 合成，开机实测能用才用，见 `COPY_OK`）。
   - 顶层画布 `fxTop`（飞金豆、成就横条）平时是空的，空着就藏起来，不让浏览器每帧多合成一整屏透明图层。
5. **窗口缩放。** 手机浏览器收放地址栏 / 工具栏会连着来一串 resize。原来每来一次：三张大画布重新分配 + 全部像素字重贴一遍（100 多毫秒）。现在画布尺寸没变就不重设；像素字只在放大倍数真的变了才重贴，并且等缩放停下 150 毫秒再贴（`pixKey`）。
6. 指针：原来每个 `pointermove` 都量一次画布位置（`getBoundingClientRect`），现在只在窗口变了时量（`cvBox`）。

顺手修了一个老毛病：「下一个」预告是镀金的时候，金星冒在预告左下方（屏幕坐标被当成世界坐标又缩了一遍），现在冒在预告上。

### 高负载（美梦快堆满）的优化

- **物理**（满堆时主线程的大头）：Matter 判断两个多边形撞没撞（`Collision._overlapAxes`）是把两边所有顶点对每条轴都投影一遍，占物理的三分之一。换成结果相同的快算法（文件开头那段）：自己的轴投自己的顶点只算固定的 2 个点；对方的顶点从上一条轴的极值点「爬」过去。`tools/perf_web.cjs --scene sat-check` 让新旧两个算法同时算、逐次比较：143 万次调用，重叠量最大差 5×10⁻¹²，选的轴、撞没撞的判断零差异——碰撞、合成、手感不变。`?nosat` 用回原版。迭代次数、碰撞箱都没动。没开 Matter 的「睡眠」（静止的不算）：它只在被动着的东西撞到时才叫醒，下面的东西被合掉、上面的不会醒，会悬空；而且连丢的时候整堆一直在动，本来也省不下多少。
- **画球**：普通精灵直接算好矩阵贴一张图（`setTransform` + `drawImage`），不走 `save / translate / rotate / scale / restore` 那一串。
- **镀金球**：原来每个镀金球每帧都在一张小画布上现合成「精灵 + 反光带」再贴——小画布每帧在变，浏览器每贴一次就要重新上传一次贴图，几十个镀金球时这是绘制里最贵的一项。现在反光带扫到每个位置的样子预先合成成一张图集（`glintAtlas`，每级一张，第一次用到才做，11 级全做约 15MB），画的时候查一格。图集里带子按整数像素走，和逐帧现算的最多差 1 像素；图鉴、成就头像、教程仍然逐帧现算（`paintGlint`，也改快了：带子预先画成小图，像素和原来一样）。
- **特效**：原来每个特效每帧复制一份对象来换坐标，满屏金星时全是垃圾回收；现在原地换、画完换回。每步清理特效也改成原地压紧。

### 量出来的数

`tools/perf_web.cjs`，400×860 @3 的视口（画布 1080×2112），基准堆 `tools/perf_pile.json`（美梦快堆满，150 个球）边连丢边量；「4 倍降速」是把主线程拖慢 4 倍模拟慢手机。两次测量、中间歇够了的数：

| 场景 | 原来 | 现在 |
|---|---|---|
| 满堆，显卡画布，4 倍降速：帧率（显示器 180Hz） | 43 / 51 | 93 / 106 |
| 同上，每帧脚本耗时（其中物理每步） | 22 / 18 ms（11.0 / 10.7） | 8.4 / 7.0 ms（9.3 / 8.6） |
| 一半镀金的满堆（`perf_pile_gold.json`），同上：帧率 | 13 / 23 | 71 / 87 |
| 满堆，软件画布（没有硬件加速），4 倍降速：帧率 | 7.7 / 8.6 | 12 / 14 |
| 空场（刚开一局），软件画布，4 倍降速：帧率 | 40 / 42 | 59 / 60 |
| 满堆，显卡画布，不降速：每帧脚本耗时（物理每步） | 1.55 ms（1.96） | 0.88 ms（1.55） |

改前改后的空场画面在 4 种视口（手机、小窗、桌面、大屏）下逐像素比过：差别只有背景个别行的边界挪了一个物理像素（背景换了一层画，取整的地方不同）、半透明混合差 ±1 色阶；堆满的画面两边随机数走的不一样、没法逐像素比，是并排看的。流程用 `tools/smoke_web.cjs` 走过（普通局、灌水、失败、带堆进美梦、连丢、摇一摇、暂停、大肥鱼时停、教程、开始页往返、窗口缩放、桌面和大屏视口），无报错。

### 帧率小窗（`?fps`）

网址加 `?fps`，左下角三行小字（英文，免得把用不上的字收进字模图）：

```
120Hz  fps 118  max 12ms                    屏幕刷新率 · 实际帧率 · 这半秒里最长的一帧
logic 3.1ms (phys 2.4)  draw 0.9ms  60 steps/s   每帧逻辑（其中物理）· 绘制各花多久 · 每秒走几步（正常 60，少了就是在放慢）
balls 152  cv 1080x2112  400x791@3.00       球数 · 画布大小 · 窗口大小 @ 像素比
```

怎么读：`fps` 明显低于刷新率、`logic` 很高 → 物理算不过来；`logic` + `draw` 加起来只有几毫秒帧率却上不去 → 时间花在浏览器画画布上（多半是画布没有硬件加速）；`fps` 是满的还觉得卡 → 把截图和机型发回来再看。

### 没验证 / 留着的

- **没有在小米 15 上验证过**，也没有任何真机数据；上面的「一进去就卡」是按节奏问题修的，电脑上能复现并且修好了，但不能保证真机上就是它。
- 画布没有硬件加速的浏览器上，满堆时大头是「画 100 多万像素旋转的精灵」，这轮没动（要降分辨率才省得下来，会糊，没做）。
- 物理剩下的大头是 Matter 自己的求解器（迭代次数 10 / 8 是调过手感的，没动）。
- **微信版同一轮也改了**（wxgame 分支）：同样的插值、按步推进、追帧上限、分离轴快算法；另外它自己多一层开销（画布上下文是带变换跟踪的代理，一个球十来次调用），加了用原生上下文直贴的快路径，和原路径逐像素对照一致。见那边的 `wxgame/validation/帧节奏与高负载优化-20261114.md`。同样没有真机数据。
- 测量脚本要 playwright：`NODE_PATH=$(npm root -g) node tools/perf_web.cjs . --gpu --throttle 4`，选项见文件头。笔记本连着跑会降频，后几秒的数会差好几倍，两次之间歇 20 秒。

## 改文案（text.json）

游戏里**绝大多数**文案都在 [`text.json`](text.json)：标题、开始页玩法说明、各页面文案、**按钮文字**、图标按钮的悬停提示、图鉴、成就页、合成特效的大字标题、11 个物品的全名、简称和**图鉴小故事**（普通页「故事」、镀金页「镀金故事」）、27 个成就的名字/说明/隐藏成就的提示，以及调试模式（`?debug` / `?showcase`）里的字。**例外是署名页**：它由 [`docs/署名与授权.md`](署名与授权.md) 生成后写进 `text.json`，改法见下一节。

1. 直接改 `text.json`（普通 JSON，键是中文；`_说明` 开头的键只是注释），**署名页除外**。`{n} {a} {b} {date} {page} {total} {mode}` 是程序填的数字/日期，别删，位置可以挪。
2. 在本目录跑 `python tools/build.py`。它会：检查文案有没有缺项、空文案、不认识的占位符、署名页标记是否成对 → 生成 `text.js`（`window.TEXT`，`index.html` 在 `game.js` 前加载）→ 新文案里的新字自动补进字模图 → 把 `text.js` / `game.js` / `pixui.js` / 字模图在引用处的 `?v=` 换成文件内容哈希（文件没变就不变，改了浏览器一定拉新的）。
3. 刷新网页看效果；字变长了留意版面放不放得下（构建不会检查，按钮尤其容易撑宽）。

### 署名 / 授权文案（唯一源）

游戏署名页的措辞不直接写在 `text.json` 里，只认 [`docs/署名与授权.md`](署名与授权.md)：

1. 改 `docs/署名与授权.md` 的 `## 游戏署名页`：标题 + 3 段正文。
2. 跑 `python tools/build.py`。构建会先把「游戏署名页」写回 `text.json`；微信版分支上还会同步 `wxgame/reference-web/text.json` 和 `text.js`。
3. **不要直接改** `text.json` 的「署名页」或微信版的 `wxgame/reference-web/text.js`，下次构建会覆盖。只检查生成物有没有落后：`python tools/attribution.py --check`。

署名是授权要求，改措辞前先和作者确认。

**要点**：
- `text.js` 是生成物，别手改；`text.json` 才是源头。`game.js` 里读 `TX.组.键`，构建会检查用到的键 `text.json` 里都有。`index.html` 里不再有写死的文案（只剩 `<title>`，运行后会被「标题.游戏名」覆盖）。
- 隐藏成就（有「提示」的）没达成时，名字显示成 `？？？`、说明位置显示「提示」。成就说明里的数字（1000 分、3 条大肥鱼…）和 `game.js` 里的门槛是**两处独立的**，改数字要两边一起改。
- **强制换行**：图鉴、成就的小故事是自动换行的；想在某处硬换行，在字符串里写 `\n`（JSON 的换行写法，不是什么特殊标记），换行后各行居中/靠左的规则不变。
- **得分门槛**：成就 s1–s5 的「分数」是得分门槛（程序用它判定），说明里的 `{n}` 自动填它，只改一处就行。
- **图鉴小故事**：点图鉴里的格子，名字下面显示这一格的小故事，自动换行、居中。预留 2 行（约 40 字）的高度，写超了会多一行、卡片变高。镀金页 11 段连起来是一个完整的故事：金手指国王（魔改自点石成金）——先是食物（小笼包→饭团→面窝→白米饭→泡面）变成金子，再是国王用的 AI（小螃蟹→小鲸→大小姐→豆包→饭盆小鲸）也变成了金子，最后大肥鱼收尾。顺序按 11 级排，改某一段时留意前后衔接。镀金饭团的海苔、白米饭的碗、泡面的杯子、角色的脸是不镀金的（美术上就是原色），故事里借了这个梗。
- **成就小故事**：每个成就在「成就名单」里有一句「故事」，选中**已达成**的成就时，显示在详情（图标、名字、说明、获得时间）下面：一行放得下就居中，放不下（换成两行）就整段靠左；预留 2 行（约 40 字）；没达成时这块是空的，不剧透。想一次看全所有成就故事和图鉴小故事：网址加 `?debug`，图鉴 22 格和 27 个成就全部点亮（只在内存里，不写存档，关掉就恢复）。图鉴全收集（`m2`）的故事是预定好的结局：「可惜，那只鲸鱼最终迟到了一个月。国王，饿死了……」。
- 新增成就：`game.js` 的 `ACH` 加一项（id/图标/门槛），`text.json` 的「成就名单」加同 id 的文案（名、说明、故事）；构建会检查 id 对得上、三项齐全。
- 新增别的文案位置：`text.json` 加键，`game.js` 里用 `TX.组.键`（带数字的用 `fmt(模板, {n: ...})`）。

## 改美术的流程

1. 原图放 `art/`（绿幕 `#00FF00` 的格子表，文件名带版本号，不覆盖旧的）。
2. 改 `tools/make_sprites.py` 里的 `TIERS`（来源文件、格子序号、色板、对比度）和 `GRIDS`（每张表几列几行）。改了名字或大小，同步 `game.js` 的 `TIERS`。
3. 在仓库根目录跑：
   ```bash
   PYTHONUTF8=1 python tools/make_sprites.py
   ```
   需要 `numpy pillow scipy`。脚本会读 `assets/`（不进 git，见下）。
4. 看 `sprites/tiers_preview.png`，再进游戏看。

### 手修精灵（`override`）

某一级的精灵如果用户在画图里直接改过成品，就把改好的 PNG 放进 `art/手修/`，在 `make_sprites.py` 的 `TIERS` 里给那一级加 `override='手修/xxx.png'`：脚本原样用这张图，**跳过自动像素化**，碰撞箱和镀金版 `gNN.png` 照常由它生成。不加的话，重跑脚本会把手改冲掉。

- **2026-11-08 大小姐（第 8 级）**：用户在自动生成的 `t08.png` 上点了嘴（3 个像素，约在 (31–33, 46–47)，棕粉色），文件是 `art/手修/t08_Claude大小姐_点嘴.png`。这 3 个像素落在 `face_masks/08_Claude大小姐_脸部遮罩.png` 的保留原色区里，镀金版嘴也是原色。
- 改了 `sprites/` 里的图后，把 `game.js` 顶部的 `SPRITE_V` 加一（所有精灵图请求都带 `?v=`），再把 `index.html` 里 `game.js?v=` 加一，否则装过旧版的浏览器会读缓存。

### make_sprites.py 依赖的 assets/（作者的私有素材，本仓库没有）

`make_sprites.py` 的输入有一部分是动画项目的私有物件库、调色板（小包子、饭团、大饭盆、泡面、烧饼，以及背景、角色设定图），不在本仓库里，所以**这个脚本在公开仓库里跑不起来**。它的产物（`sprites/`）已经提交，直接玩、改玩法、改文案都不需要它；`art/` 里的 GPT 原图和 `tools/make_ach_icons.py` 等其余脚本不依赖私有素材。想换美术，参照下面「像素化怎么做的」自己出图、自己像素化即可。

### 像素化怎么做的（和动画对齐）

照动画项目 `代码工程/spriteize.py` 的 `spriteize_flat`：按角色色板量化（小鲸 `帧库/调色板_精简.npy`、大小姐 `帧库/调色板_Claude娘全.npy`、豆包从定稿设定图取 20 色、其余从原图自取 16 色），每个色板都补两档深色防止小眼睛被吞；2 倍尺寸量化后 2×2 取众数缩回；去一遍孤点；1 像素外轮廓 `#2B2622`。大小姐对比 1.25、豆包 1.2（动画里大小姐也用 1.2）。小螃蟹不去孤点（眼睛只有两格宽）。试过动画的「内轮廓压深」和两遍去孤点，在头像这个尺寸会把眼睛抹掉，所以没用。

碰撞箱是精灵不透明像素的凸包，物件按自己的形状滚（面窝的孔也被凸包填上，不会卡东西）。

## 用户定下的美术方向（别走回头路）

- **物件和头像裸着进游戏，按形状做碰撞**，不要装进圆球里（那样就成了纯换皮）。所以挑圆润的素材。
- 角色头：正面、视角摆正、轮廓圆；**用大眼睛表达情绪，嘴巴弱化，不要 ω 嘴**（大小姐的嘴是用户手点的 3 像素小嘴，就这个量级）。
- 画风和动画的像素风对齐：GPT 只出日系 Q 版插画（和定稿图同画风），**像素化由我们的脚本做**，不让 GPT 直接出像素图。
- 被否掉的：v1「铸币大头」（太像别家风格）、v2 毛绒扁平色块（`art/废弃/`）。
- 鲸鱼、小螃蟹必须是**对原形象的再创作**（DeepSeek 鲸鱼图标、Clawd），要一眼认得出，不能让 GPT 自由发挥成别的鲸鱼/螃蟹。
- 烧饼特征不明显 → 换成同画风同配色的面窝（要真正的面窝，不是开个洞）。
- 等级顺序刻意把小鲸、大小姐、豆包穿插开，避免合成序列单调。
